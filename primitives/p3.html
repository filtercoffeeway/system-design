P3 · Replication & the consistency ladder

What it is: keeping copies of data for durability, availability, and read scale — and choosing how consistent those copies must be.
Reach for it when: you need to survive node loss, serve more reads, or place data near users.
The lever: single-leader (simple, follower lag), multi-leader (write-anywhere, conflicts), leaderless/quorum (Dynamo R+W>N). The consistency ladder is the dial: strong → bounded-staleness → read-your-writes → eventual. CAP: under partition pick availability (stale, AP) or consistency (error, CP).
New problem it hands you: replication lag → read-after-write anomalies. Multi-leader/leaderless → write conflicts needing version vectors or last-writer-wins. Stronger consistency → higher latency, lower availability under partition.
Exemplified by: KV store, RDBMS, Kafka (ISR), Object store.

1 · The problem it solves

A single copy of data dies with its node and serves only as fast as one machine. Replication keeps multiple copies so you survive failures, scale reads, and place data near users. The catch is that copies drift apart, so you must also choose how consistent they have to be.

2 · The replication ladder

Rung 0 — one copy

Simplest possible. Dies with its node, and serves only as fast as one machine.

Bottleneck: no durability, no read scale.

Rung 1 — single-leader, async replication

All writes go to one leader; it streams the change log to read-only followers. Buys durability (copies survive node loss) and read scale (fan reads across followers). The leader is still the single writer, and followers lag.

Bottleneck: replication lag → a read of a follower right after a write may not see it (read-after-write anomaly); writes still cap at one node.

Rung 2 — synchronous / quorum replication

Wait for replicas to acknowledge before confirming a write. No stale reads if you read a quorum — at the cost of write latency. The leaderless form (Dynamo-style) drops the leader entirely: write to W replicas, read from R, and choose R + W > N so the read and write sets must overlap. Worked, N=3:

graph LR
  W["write v2 (W=2)"] --> A["A: v2"]
  W --> B["B: v2"]
  C["C: v1 (missed it)"]
  R["read (R=2) from B,C"] --> B
  R --> C
  R --> M["see v2 & v1 → newest wins → v2"]
N=3, W=2, R=2 → W + R = 4 > 3 → write set {A,B} and read set always overlap write v2 to {A,B}; C still holds v1 read from {B,C}: gets v2 (B) and v1 (C) → version says v2 newer → return v2 ✓ if instead R=1 and you read {C}: returns stale v1 ✗ (W+R = 3, not > N)

So the quorum inequality isn’t a slogan — it’s the exact condition that the nodes you read are guaranteed to include one that saw the latest write.

Bottleneck: higher latency (wait for a majority), and the leaderless/multi-leader forms admit write conflicts (next section).

3 · The consistency ladder (the dial)

Orthogonal to where writes go is how consistent reads must be — a dial, not a switch, from most expensive to loosest: strict serializable → linearizable → bounded staleness → read-your-writes → eventual. Pick the loosest rung the requirement tolerates. CAP: under a network partition you must drop either consistency (serve stale, AP) or availability (return an error, CP). PACELC adds the part everyone forgets — even with no partition (E, “else”) you trade latency vs consistency on every request.

4 · Conflicts & version vectors

The moment two replicas can both accept a write (multi-leader or leaderless), they can diverge. A version vector — a per-replica counter — detects whether two versions are causally ordered or genuinely concurrent:

start: cart = {} , vv = [A:0, B:0] A adds milk: value={milk}, vv=[A:1, B:0] B adds eggs: value={eggs}, vv=[A:0, B:1] (B didn't see A's write) compare [A:1,B:0] vs [A:0,B:1]: neither dominates → CONCURRENT → conflict resolution: merge ({milk,eggs}) or last-writer-wins (one silently lost)

Last-writer-wins is simplest but silently drops one update; a mergeable type (a CRDT, like a set-union cart) keeps both. The point is you can’t avoid the choice once two writers exist.

5 · The new bottleneck it hands you

Replication lag is the headline cost: read a follower right after writing the leader and you may not see your own write (read-after-write anomaly). Fixes — route a user’s reads to the leader for a few seconds, or track a version and wait for a replica to catch up. Multi-leader/leaderless introduce write conflicts needing version vectors or last-writer-wins (which silently drops data). Stronger consistency costs latency and availability: a quorum write waits for a majority, and a linearizable system can’t serve a minority partition.

6 · Real-world example

Amazon DynamoDB & Google Spanner

DynamoDB exposes the dial directly: a read can be eventually consistent (cheaper, may be stale, hits any replica) or strongly consistent (reads the leader replica, costs more). Its writes are quorum-replicated across three Availability Zones. At the opposite end, Google Spanner buys external consistency (linearizable, globally) by using TrueTime — GPS- and atomic-clock-synchronized time with a bounded uncertainty interval — and deliberately waiting out that uncertainty on commit. The contrast is the whole ladder: DynamoDB lets you pay less for staleness; Spanner pays latency for global strong consistency.

7 · Replicating read-only config: local evaluation & where “serve stale” fails

Replication is not only for databases. A large class of systems replicate a read-only control plane — feature-flag rules, routing tables, auth policies, service-discovery state — out to every application process so that hot-path reads are answered locally, in memory, with zero network hops. It is the same single-leader async pattern as Rung 1: a backend is the sole writer, and the “followers” are your app servers. The twist is that the replicated artifact is a rule set, not rows, and the replica is re-evaluated against every request rather than read out directly.

Derive it as a ladder

Start with the simplest thing and watch it break.

Rung 0 — call the control-plane API on every check. correct and always fresh, but each check is a network round-trip on the hot path. 1 flag check per request × 5k req/s × 50 app servers = 250k calls/s into the config service, each adding ~1–50 ms RTT to your latency. → dies on both latency and fan-in almost immediately. Rung 1 — replicate the whole rule set to each process, evaluate locally. init: one fetch of all rules into memory; every check is then 0 hops, ~microseconds. refresh: a background thread re-pulls the rule set every ~10 s and swaps it in atomically. cost: eventual consistency — a rule edit is invisible until each replica's next poll (bounded staleness ≈ the poll interval), and reads never touch the primary.

Rung 1 is the standard answer, and it is a textbook consistency-ladder trade: you accept ~10 s of staleness (a rung of bounded staleness from §3) to buy zero-hop reads and read availability that survives the primary being slow or briefly unreachable. The exposure/event telemetry flows the other direction on its own schedule — buffered and flushed on an interval — which is P1 batching, not replication; keeping the two paths distinct is the whole point.

Where “serve last-known-good” quietly fails

The reassuring property of async replication is graceful degradation: if a poll fails, the replica keeps evaluating against the copy it already holds. That intuition is correct — but it only protects you against failures the replica recognizes as failures. Two gaps slip past it, and both surfaced in a real incident where a feature-flag SDK key was deleted and every gate in production started returning false.

Failure A — cold start (a replica with no snapshot). A process that boots *after* the key is deleted never completes its init fetch (401). There is no last-known-good to fall back to — the replica is empty from birth — and an unknown gate defaults to false. Any pod that autoscaled, redeployed, or crash-looped came up blank; pods initialized *before* the deletion kept serving correct values. → the outage looked staggered, not instant, which is the tell for this mode. Failure B — authoritative-empty (the primary replicates "nothing", successfully). Depending on SDK version, the endpoint answers 200 with an empty rule set because the key no longer maps to a project. That is not an error the replica rejects — it is a *successful* update — so it atomically overwrites good in-memory state with empty. → even a long-lived, already-initialized replica flips to false.

The distinction is the P3 lesson worth remembering: stale-read tolerance defends against transport failures, not against a cold replica or against an authoritative “there is nothing here.” A dropped poll is safe; a poll that succeeds and returns emptiness is not. This is the same family of hazard as last-writer-wins in §4 — a well-formed write (here, of nothing) silently destroying good state.

The fixes, in replication terms

Both holes have standard patches, and both are ordinary replication ideas:

HolePatchWhy it’s a replication primitive
Cold start with no snapshotBootstrap / seed the replica from a secondary source (a rules blob in S3/Redis/a baked-in file) at initSeeding a new follower from a snapshot before it joins the stream — exactly how a database bootstraps a fresh replica instead of starting empty.
Authoritative-empty overwriteExplicit per-read defaults at the call site, and treating “empty rule set” as suspect rather than authoritative Choosing the safe state when the replica can’t be trusted — the same availability-vs-correctness call CAP forces under partition.

Note the second fix is really a design decision, not a config toggle: for a kill-switch gate, false means “feature off,” so an empty replica fails closed; for an entitlement gate, false might lock every user out. Decide the safe direction per gate rather than inheriting the SDK’s implicit default.

Statsig feature flags

Statsig’s server SDKs are a clean instance of this whole pattern. initialize() pulls the entire rule set via download_config_specs; every checkGate() is then evaluated locally against in-memory rules with no network call, and a background thread re-polls on a ~10 s default interval (configurable, e.g. Go’s ConfigSyncInterval) — async single-leader replication of a control plane. Exposures and events flow back batched on a ~60 s flush (or on shutdown()), the P1 half of the design. Statsig supports bootstrapping from a data adapter (Redis/S3) precisely so a process that can’t reach the origin comes up seeded instead of empty — the Failure-A patch above. When an SDK key is deleted, newly started processes fail auth at init and evaluate every gate to its default false, which is the exact cold-start hole that bootstrap seeding and explicit defaults are there to close.

At very large fleets, per-process polling itself becomes a fan-in bottleneck on the config origin — thousands of replicas each pulling every 10 s. The next rung is a proxy/CDN tier: one process fetches specs and serves the fleet, or replicas read from a CDN/edge cache. That is P11 edge caching layered on top of P3 — another lever, another bottleneck.

8 · Applying it in a design

State the requirement first, then pick the rung: "this counter can be eventually consistent, so I’ll read from any replica; this balance must be read-your-writes, so I’ll pin the user to the leader or wait for a version."

9 · Pitfalls

  • Defaulting to "strong consistency everywhere" and eating needless latency.
  • Last-writer-wins silently losing concurrent updates.
  • Reading your own writes from a lagging replica.
  • Assuming a replica “serves last-known-good” on failure — it doesn’t survive a cold start (nothing to serve) or an authoritative-empty response (overwrites good state). Seed replicas and set explicit defaults.
