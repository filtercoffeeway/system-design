P21 · Streaming aggregation & windowing

What it is: continuously turning an unbounded, out-of-order event stream into per-window results (counts, sums, distinct-counts, top-K, percentiles) as the data flows — instead of re-running a batch job.
Reach for it when: real-time metrics, click / impression aggregation, dashboards, trending, billing meters, fraud — you need a rolling answer over a stream that never ends.
The lever: bucket events into windows by their event time; keep a per-window partial aggregate in state; use a watermark to decide when a window is complete enough to emit; checkpoint the state so a crash doesn’t double-count.
New problem it hands you: state grows with keys × open windows; the watermark is a completeness-vs-latency dial; and late data after the watermark forces a drop / side-output / re-emit choice. State size and delivery semantics become the hard parts.
Exemplified by: Datadog metrics, Top-K trending, click aggregation; composes P1 batching, P2 partitioning, P7 partial aggregation, P9 idempotency.

1 · The problem it solves

You have an endless stream of events — clicks, page views, metric points, transactions — and you need a continuously updated answer: “clicks per ad per minute,” “p99 latency this 5-minute window,” “distinct users in the last hour,” “top-10 trending items right now.” A batch job that recomputes from raw storage is both too slow (minutes-to-hours late) and too expensive (it rescans everything each run). What you want is incremental aggregation: fold each event into a running result the moment it arrives.

Two facts make this hard, and they are the whole subject. First, the stream is unbounded — “the total count” is never final, so you must slice time into windows to ever emit anything. Second, events arrive out of order: a click that happened at 12:00:59 can reach you at 12:01:03, after events from 12:01. So “is the 12:00 minute done?” is not a question the clock on the wall can answer — you need a principled notion of stream progress. That notion is the watermark.

2 · How it works

The clean mental model is the Dataflow model (Google): every streaming aggregation answers four questions.

QuestionAnswered by
What is computed?the aggregation function — count, sum, a sketch (§3)
Where in event time?the window assignment (tumbling / sliding / session)
When in processing time is it emitted?the trigger — usually “when the watermark passes the window end”
How do refinements relate?the accumulation mode — discard / accumulate / accumulate&retract

Event time vs processing time

Every event carries an event-time timestamp (when it actually happened) that is different from its processing-time (when your system saw it). Windowing on processing time is trivial but wrong — a network hiccup or a consumer restart would shove events into the wrong bucket and your “12:00 minute” would silently depend on pipeline health. Correct aggregation windows on event time, which is exactly what creates the out-of-order problem.

Windows, state, and the watermark

Each event is routed by key (P2 — same key to same worker, so its state is local) and assigned to one or more windows by its event timestamp. Per (key, window) the engine keeps a partial aggregate in state and folds each event into it — storing the combiner (a running count/sum/sketch), never the raw events (P7). A watermark is a moving lower bound on event time: “I believe I have now seen every event with timestamp ≤ T.” It is usually derived as max-seen-event-time − allowed-lag. When the watermark passes a window’s end, the window is declared complete, its trigger fires, and the aggregate is emitted; the state for that window can then be dropped.

The watermark is the heart of it: it converts “wait forever for perfect data” into “wait a bounded, tunable amount, then emit.”

Triggers & accumulation

Beyond the default “fire on watermark,” triggers can fire early (speculative results before the window closes, on a processing-time timer or every N events) and late (a refined result when a straggler lands after the watermark). Accumulation mode says how those firings relate: discarding (each firing is a delta), accumulating (each firing is the full running result, replacing the last), or accumulating & retracting (emit a retraction of the old value plus the new — needed when the downstream can’t just overwrite).

Exact vs sketched aggregates

What you keep per window matters as much as the window. An exact distinct-count needs the full set of keys seen; at high cardinality that state is enormous. So streaming aggregation leans on mergeable sketches — small, fixed-size, approximate summaries:

distinct countHyperLogLog~1–2% error for ~KB instead of storing every id

Sketches are the reason a metrics system can hold millions of series in RAM: they are mergeable, so each partition builds its own and a central step merges them (P7) without ever shipping raw points.

4 · The new bottleneck it hands you

(a) State size. Aggregation state is keys × open windows × per-window aggregate size. High key cardinality or sliding windows (which put each event in many overlapping windows) make it explode. Relief escalates: store the combiner not raw events; use sketches (§3) so per-window state is fixed-size; back the state with an on-disk store like RocksDB (P17) so it can exceed RAM; and aggressively evict windows once the watermark closes them (so tumbling beats sliding, and sessions must be able to expire).

(b) The watermark is a completeness-vs-latency dial. Advance it aggressively (small allowed lag) and you emit fast but close windows before stragglers arrive → undercount. Advance it conservatively and results are correct but late. Worse, a watermark is the minimum across all input partitions, so a single idle or lagging partition holds back the whole pipeline — no windows anywhere can close. Idle-source detection and per-partition watermark tracking exist precisely to stop one stuck shard from freezing all output.

(c) Late data. Once the watermark has passed a window, an event for that window is late, and you must pick a policy: drop it (fast, lossy — and silent unless you count drops), route it to a side-output for separate reconciliation, or set an allowed-lateness and re-emit the updated window. Re-emission means the downstream sees the same window twice with different values, so it must be idempotent or able to retract (P9) — upsert by (key, window), don’t +=.

(d) Exactly-once over stateful operators. Because the aggregate is state, recovery after a crash must restore state that is consistent with the input position, or you double-count on replay. That is the checkpointing problem below — the hardest correctness property in the whole primitive.

Checkpointing: consistent snapshots of distributed state

The engine periodically snapshots every operator’s state together with the input offsets that produced it, so on failure it restores all state and rewinds the sources to the matching offsets — exactly-once with respect to state. The elegant trick (Flink’s, below) is to inject numbered barriers into the stream: when an operator has received the barrier on all its inputs, it snapshots its state and forwards the barrier. The barrier cleanly separates “events before the snapshot” from “events after,” so the snapshot is globally consistent without stopping the world — a variant of the Chandy-Lamport distributed-snapshot algorithm.

5 · Real-world example

Apache Flink

Flink is the reference implementation of this primitive. It processes in event time with watermarks, keeps large keyed state in an embedded RocksDB state backend (so aggregation state spills to local disk and can far exceed RAM), and gets exactly-once via asynchronous barrier snapshotting — its variant of Chandy-Lamport. The checkpoint coordinator has sources record their offsets and inject numbered checkpoint barriers into the stream; each operator, once it has aligned the barrier across its inputs, copies its state asynchronously (RocksDB’s copy-on-write enables incremental snapshots of only the changed state) and forwards the barrier. On failure the job restarts from the last checkpoint and the sources rewind to the recorded offsets, so no event is double-counted. Alibaba runs Flink for real-time analytics at Singles’ Day scale (billions of events/s peaks), and it underpins streaming pipelines at Netflix, Uber, and Pinterest.

Google MillWheel / Dataflow

The watermark abstraction this whole page rests on was formalized by Google’s MillWheel and the Dataflow model (Akidau et al.). A watermark is the threshold at which Dataflow expects all data for a window to have arrived; when it passes the window end the window fires, and anything arriving afterward is late data handled by triggers and accumulation. MillWheel’s own note is instructive: most aggregate pipelines don’t need 100% accuracy — they want a mostly complete view in a reasonable time, which is exactly the completeness-vs-latency trade the watermark exposes. This model is now the industry vocabulary (adopted by Apache Beam and, in spirit, by Flink).

6 · Applying it in a design

When a system needs real-time rollups, say the sentence that shows you understand the trade: “I’ll aggregate in event-time windows, keyed and partitioned so state is local, holding a partial aggregate (a sketch when cardinality is high) in checkpointed state per (key, window); fire on the watermark with a bounded allowed-lateness and a side-output for stragglers, and make the sink idempotent so re-emissions upsert rather than double-count.” This is the standard answer for click aggregation, metrics, billing meters, and real-time trending. It sits directly downstream of Kafka: the log gives you replayable, partitioned, ordered-per-key input; this primitive turns that stream into answers.

7 · Pitfalls

  • Windowing on processing time when you mean event time — results silently depend on pipeline lag.
  • Unbounded state: no window eviction, a session gap that never closes, or storing raw events instead of a combiner.
  • One idle/lagging partition stalling the global watermark, freezing all output — forgetting idle-source handling.
  • No late-data policy → silent undercount; dropping late events without counting the drops.
  • Sliding-window state blow-up (each event in size/step windows) — use tumbling or a sketch if you can.
  • Re-emitting refined windows into a non-idempotent sink (+= instead of upsert by (key,window)) → double counting.
  • Treating an approximate sketch as exact — know the error bound before you put it on a billing invoice.
