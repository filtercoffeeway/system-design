19 · Search Autocomplete / Typeahead

Hard constraint: return ranked completions on every keystroke in a few ms at ~106 QPS — so the answer is a precomputed top-k at each prefix served from RAM, with the hot head absorbed at the edge. The matching structure is secondary; the precomputation and the skew are the system.
Primitives exercised: P2 (partitioning / hot-key), P4 (caching), P11 (CDN / edge), P1 (batch + stream), P6 (search retrieval, sibling system S7).

This is what “how does YouTube/Google search work” usually means in an interview: the as-you-type suggestion box, not full retrieval (S7). Trie vs FST (serve-time is really a prefix→top-k KV get); materialize top-k to a capped depth; first-letter sharding is the trap; hash + replicate + edge-cache the head fixes the hot key; a streaming speed layer keeps trending fresh (rate-normalized merge); immutable index builds swap in atomically; scrubbing and fail-open are first-class.

1 · Requirements

Functional. (1) suggest(prefix) returns the top k (≈5–10) completions for a prefix, ranked by popularity/relevance; (2) it fires as the user types each character; (3) tolerate minor typos (“netflox” → “netflix”); (4) reflect trending/breaking queries within minutes, not a day. Out of scope for the core design: executing the actual search and ranking result documents — that’s the search engine (S7); mention the boundary, then set it aside.

Non-functional — these shape everything:

PropertyTargetWhy it matters
Latencyp99 < ~100 ms end-to-end; lookup itself a few msIt fires on every keystroke; a slow suggestion is worse than none and is discarded by the client.
Read:write ratiooverwhelmingly readsPopularity is aggregated offline/streaming, never per request → optimise the read path above all.
Traffic shapeextreme Zipfian skewA tiny set of short, popular prefixes is most of the load → caching the head is the architecture, not an add-on.
Freshnesstrending visible in minutesA daily batch can’t surface a term that started spiking an hour ago.
Consistencyeventually-consistent ranking is fineIt’s a hint list; being a few minutes stale on the tail is invisible to users.

2 · Capacity estimation

Numbers first — they decide where the design lands. Assume Google scale: ~5 billion searches/day, and the suggest endpoint fires on (debounced) keystrokes, ≈6 calls per search.

QUERY VOLUME 5,000,000,000 searches/day x 6 suggest calls = 3.0e10 suggest q/day 3.0e10 / 86,400 s ≈ 347,000 QPS average peak ~3x ≈ 1,040,000 QPS INDEX CORPUS — derive the size, don't assert it index the head + torso, NOT every string ever typed: ~1e9 distinct queries x ~20 chars ≈ 20-25 GB raw strings the blowup is MATERIALIZATION, not the strings: a query of length L sits in the top-k list of up to ~L prefixes -> prefix entries ≈ 1e9 queries x ~20 each ≈ 1e10 entries (after sharing) -> each entry: k=10 x (8 B ref + 4 B score) + key overhead ≈ ~200 B -> 1e10 x ~200 B ≈ 2 TB <- where the number comes from two cuts that make it tractable: cap materialization DEPTH at ~5-7 chars (deep prefixes have tiny candidate sets; scan them live in the FST) -> ~1e9 entries, 200-400 GB FST suffix-sharing + bit-packing on the strings -> several-fold smaller again -> still multi-hundred-GB: a small RAM fleet, never one box TRAFFIC SKEW (why caching dominates) top ~10,000 prefixes ≈ 50-70% of ALL suggest traffic -> a tiny edge cache absorbs the majority of requests -> the sharded fleet only serves the well-distributed long tail SERVING ~1.04M peak QPS / ~50k QPS per RAM box ≈ ~21 boxes for raw QPS -> so the real constraint is MEMORY FOOTPRINT + SKEW, not aggregate QPS LATENCY BUDGET p99 < ~100 ms end-to-end; serving lookup a few ms (walk + return cached list)

The takeaways that drive the rest: it’s a read/caching problem; the naive materialize-everything index is ~2 TB and the blowup is the per-prefix top-k entries, not the strings — so the depth cap and the FST are where the memory fight is won; aggregate QPS is small (~21 boxes), so what actually hurts is fitting the index and surviving the skew; and freshness can’t come from batch alone.

3 · API design

GET /suggest?q=net&k=8&lang=en&ctx=... 200 : { "suggestions": [ {"text":"netflix","score":0.99}, {"text":"netflix login","score":0.71}, {"text":"net worth","score":0.55}, ... ] } Client rules (offload work to the edge of the system): - debounce ~50-150 ms so not every keystroke hits the server - cancel the in-flight request when a newer character is typed - cache per-prefix results locally for the session

The endpoint is a bare keyed GET so it is trivially cacheable by a CDN. Debounce + request-cancellation on the client cut a large fraction of calls before they leave the browser — the cheapest rung of all.

4 · The matching structure — derive it, don’t assert “trie”

The serve-time job: prefix → top-k completions in a few ms. Enumerate the family and the axis that picks between them, rather than naming one and stopping:

StructureHow it does prefix→top-kCost / when it wins
Sorted term array + binary searchPrefix defines a contiguous range; scan it, sort by scoreDead simple (rung-0 baseline); range is huge for short prefixes and you re-rank per query.
Trie (prefix tree), top-k cached at each nodeWalk len(prefix) nodes, return the node’s precomputed listO(prefix length), no serve-time sort. The canonical answer. Cost: memory + rebuild of cached lists.
Ternary search treeTrie with 3-way nodesMore memory-efficient than a fat 256-way trie; slightly slower walk.
FST / FSA (finite-state transducer)Shares suffixes too; maps string→weight compactly5–10× smaller than a pointer trie — how you actually fit ~2 TB in RAM. This is what Lucene uses. Harder to mutate in place.
Succinct trie (LOUDS)Same traversal, bit-packedSmallest footprint; read-mostly, rebuilt rather than edited.

The decisive move is independent of which structure you pick: materialize the top-k completions at each prefix node ahead of time. That converts serve-time work from “range-scan + sort” into “walk to the node, return a cached list of 5” — which is the only way to hit a few-ms p99 at this QPS. Trie is the right thing to say; an FST is the right thing to ship (it makes the 2 TB fit); the precomputed-top-k idea is the part that actually matters.

node "net" -> precomputed top-k (sorted by score, computed offline) ["netflix", "net worth", "netflix login", "netgear", "net a porter", ...] walk: n -> e -> t (3 hops) then return the list. No sort at serve time.

Be precise about what “walk the trie” means once the system is distributed. At serve time nobody walks a pointer structure across the network: the request carries the whole prefix string, so the lookup is logically a KV get — key = prefix, value = its precomputed top-k list — routed to exactly one shard. The trie/FST is the storage format inside a shard: it’s how a shard packs millions of prefix→top-k entries into RAM with shared structure, not how a request travels. Keeping these two layers straight is what makes §6’s hash-sharding coherent — you can hash-shard KV keys; you cannot hash-shard a pointer walk. (Redis-backed toy designs make the KV view explicit: ZSET per prefix; the FST is the grown-up, 10× smaller version of the same mapping.)

And cap the depth. Materialize top-k only for prefixes up to ~5–7 chars (tunable per corpus). Short prefixes are where precomputation pays: candidate sets are huge and traffic is hot. Past the cap, the surviving candidate set under any node is small — tens of completions — so the shard finds the deepest materialized ancestor and scans the FST subtree live, which is a few µs over a handful of entries. This one decision cuts the naive 2 TB (§2) by ~5–10× and is the difference between a hand-wavy index and one that fits.

Typo tolerance, when the interviewer asks: run the prefix walk against a Levenshtein automaton (edit-distance ≤1–2) intersected with the FST — the same structure traversed fuzzily, no separate index. The automaton for “netflox” with distance 1 accepts “netflix”; intersection prunes the FST to states both machines accept, so cost stays proportional to the surviving candidate set, not the corpus. Cheap enough to run only when the exact walk returns few/no results — a fallback path, not the main path.

Two read tiers feed one merge. The edge answers the hot head outright. On a miss, the suggest service queries the base trie/FST fleet (stable, batch-built) and the small fresh layer (streaming), then merges the two ranked lists. Underneath, the query-log stream forks into a batch path that rebuilds the base and a speed path that maintains approximate trending counts. The user’s keystroke never waits on either pipeline.

6 · Partitioning — one box → sharding → the hot-key problem

This is the decision Chandra-style answers get wrong by stopping at “shard by first letter.” Derive it rung by rung.

Rung 0 — single in-memory trie/FST

One process holds the whole structure; every suggest walks it. Correct, and fine at small scale.

Bottleneck: the materialized index (~2 TB) won’t fit in one machine’s RAM, and one box can’t absorb ~1M QPS. Both force a partition.

Rung 1 — shard by first letter (the trap — raise it, then reject it)

Route by the leading character: an a… shard, a b… shard, and so on. Simple, but it breaks two ways — both of which a sharp interviewer will name:

Bottleneck — catastrophic skew (the hot-key problem, P2): letters and short prefixes are wildly non-uniform. The shard owning s/t/a, or hot prefixes like how…, yo…, the…, takes a huge multiple of an even share. With ~26 buckets you cannot rebalance, and you can’t split a hot letter without abandoning the alphabet rule. Worse, short prefixes are simultaneously the hottest and the most expensive (largest candidate sets), so the skew compounds.

Rung 2 — shard by hash(prefix)

Map each distinct prefix string to a shard via consistent hashing (P2). This works because serving is a KV get, not a walk (§4): the request already carries the full prefix, so it routes to exactly one shard — no fan-out, no cross-shard traversal, one network hop. The price is denormalization: “netflix” is stored in the top-k entries of n, ne, net, … which may live on different shards — but that duplication is already counted in §2’s 1e10-entry math, and it’s read-optimized duplication of an offline-built artifact, so it costs memory, not correctness. Load now spreads evenly across distinct prefixes and you can add shards smoothly.

Bottleneck: hashing fixes structural skew (the alphabet) but not popularity skew. Every request for yout still hashes to the same single shard — one viral prefix is still one hot key. Hashing balances the many, not the one.

Rung 3 — attack popularity skew directly (← the real fix)

Two complementary tools, and the second is the big one:

  • Replicate hot shards / consistent hashing with bounded loads: detect the heavy prefixes and serve them from N replicas so no single box is the ceiling.
  • Edge/CDN cache of the head (P11, P4): the top ~10k prefixes are ~50–70% of all traffic. Cache their completion lists at the edge with a short TTL (seconds–minutes). The hot keys are absorbed before they ever reach a shard, so the sharded fleet only sees the long tail — which is exactly the traffic that is well distributed. The hot-key problem you correctly smelled is mostly solved by caching the head, not by a cleverer shard key.

Rung 4 — two-tier trie

Keep the top of the tree (short, super-hot prefixes) in a small, heavily-replicated front layer; shard the deep subtrees (long, rare prefixes) across the fleet. Short-prefix queries — the hot ones — never touch the sharded tail at all.

7 · Freshness — pulling from a live stream

Where do the popularity scores come from, and how does a trending term appear in minutes instead of tomorrow? This is a lambda / kappa split (P1): a stable batch base plus a fast approximate delta, merged at serve time.

Batch layer — the stable base

A daily (or hourly) job over the query logs computes per-prefix top-k and rebuilds the serving trie/FST. Accurate and complete, but stale by up to its rebuild interval — it cannot surface a term that started spiking an hour ago.

Bottleneck: rebuild latency. By itself the batch base is always “yesterday’s popularity,” so breaking/trending queries are invisible until the next rebuild. That gap is what the speed layer fills.

Speed layer — the fresh delta

Query events stream into Kafka; a stream processor (e.g. Flink) maintains approximate popularity online, because keeping an exact count per distinct query at ~1M QPS is infeasible in memory:

  • Count-Min Sketch for frequency in fixed memory — a few hash-indexed counter arrays; it can over-count a little but never under-counts, in O(1) space per query instead of one counter per distinct string.
  • Space-Saving / heavy-hitters to keep the top-k per prefix without storing every query that was ever typed.
  • Exponential time decay on the counts, so “trending” means rising now, not popular all-time — a term that spikes can outrank an evergreen one within minutes.

Merge at serve time — and how the scores are actually made comparable

The suggest service consults the stable base and the fresh top-k layer and merges the two ranked lists before returning. A query that started trending minutes ago shows up via the speed layer; later the batch layer folds it into the base and the speed layer’s decayed entry ages out.

“Merge two ranked lists” hides the hard part: the scores are incomparable. The base score is a count over ~a day; the fresh score is a decayed sketch count over ~minutes — raw magnitudes differ by orders of magnitude, so naive interleaving either drowns the fresh layer or lets it hijack every slot. Normalize both to rates, then boost:

base_rate(q) = batch_count(q) / batch_window (e.g. per-second, all-day avg) fresh_rate(q) = decayed_count(q) / effective_window (per-second, last ~10 min) trend_boost(q) = fresh_rate / (base_rate + ε) ε guards divide-by-zero for new queries score(q) = base_rate x clamp(trend_boost, 1, B) B ≈ 10-50 caps the hijack example: "<celebrity> news" base 2M/day ≈ 23/s; spikes to 500/s over 10 min -> boost ≈ 21x -> jumps from rank ~40 to top-3 while the spike lasts, decays back as the fresh counter cools. An evergreen "netflix" (flat rate, boost ≈ 1) is untouched.

Two guards matter as much as the formula. Cap the boost (the clamp): an unbounded ratio lets a coordinated burst — or a CMS over-count on a rare string — take over the suggestion box. And require minimum support: a query must be seen from ≥N distinct users before the fresh layer may surface it at all, which simultaneously blocks bot manipulation and the privacy failure of echoing one person’s typed string to the world (see §10).

8 · Rebuild & swap — shipping a new multi-hundred-GB index with zero downtime

“The batch job rebuilds the base” is where most answers stop and where staff-level questions start: how does a fleet of RAM-resident shards cut over to a new build while serving ~1M QPS? Derive it.

Rung 0 — mutate the live structure in place

Apply count changes directly to the serving trie: bump a counter, re-sort the node’s top-k.

Bottleneck: three independent killers. (1) Write-rate: ~350k QPS of count updates against the structure you’re reading at ~1M QPS means lock contention or torn reads on the hot path. (2) The compact structures that make the index fit (FST, succinct tries) are build-then-serve — they achieve their size precisely by giving up in-place mutability. (3) One bad update has no rollback. In-place mutation dies on the same axis three ways; the fix is to stop mutating.

Rung 1 — immutable versioned builds, atomic pointer flip (← the answer)

The batch job writes each shard’s new segment as an immutable, versioned, checksummed artifact to blob storage. Each shard node then: downloads its segment vN+1, loads it alongside the live vN, warms it (page it in, verify checksums, replay a sample of recent real queries against it), and finally flips a single atomic pointer so new requests hit vN+1. In-flight requests finish on vN; it’s dropped when its refcount hits zero. Rollback is the same pointer flip in reverse — vN is still on disk.

Bottleneck — the swap costs 2× RAM. During load-alongside, a node holds two full copies of its segment. At multi-hundred-GB fleet-wide that headroom is a real capacity line item you must provision, not a footnote. Alternatives that trade the axis: rolling swap — pull one replica out of the load balancer, swap it cold, re-add, repeat — needs N+1 replica capacity instead of 2× RAM per node (and you already have replicas for the hot shards, §6); or mmap the segment and let the OS page cache hold the hot part, so “2×” is 2× of the warm set, not the whole file — at the cost of page-fault tail latency on cold prefixes.

The mixed-version window — say why it’s fine

Shards flip at different times, so for some minutes a user’s ne may be served by build N while net comes from N+1 — the two lists can disagree about a completion’s rank or existence. This is fine, by design: §1 already accepted eventually-consistent ranking, suggestions are hints with no cross-request invariant, and the edge cache (§6) was already serving results up to a TTL stale. The mixed-version window is just one more bounded staleness source, strictly smaller than the ones already accepted. (If you ever needed cross-shard version agreement, you’d pay for it with a coordinated flip — a barrier via config service/ZooKeeper — and you’d be paying for a property this product doesn’t need.)

Canary the build, not just the code

A corrupted or skewed build is the scariest failure — it serves fast, valid-looking, wrong answers fleet-wide. Treat each index build like a deploy: flip ~1% of nodes (or mirror shadow traffic to vN+1), watch suggestion CTR, empty-result rate, and p99 against the vN baseline, then promote or auto-rollback. Guardrails in the builder too: refuse to publish a build whose entry count or size deviates >X% from the previous one — a half-empty query log (upstream outage) must not become tomorrow’s empty suggestion box.

9 · Ranking — beyond raw frequency

Popularity is the baseline signal, not the ranker. Production systems re-rank with a model over: query frequency + recency/trend, the user’s own history, location/language, session context (the previous query), and — for YouTube specifically — video-side signals like watch-time, freshness, and channel authority. Mechanically it stays cheap: candidate generation produces the ~50–100 completions for a prefix (frequency-ordered, from the trie/FST), then the model re-ranks only that small candidate set. You never run the model over the whole corpus — only over what a prefix already narrowed it to. Personalization is the same shape: candidate-gen stays global, personalization is a re-rank of the small set, so it never blows up the index.

10 · Production concerns — scrubbing, privacy, failing open

Three things real autocomplete systems cannot skip, and most interview answers do.

Scrubbing: suggestions are speech the product utters

A search result is someone else’s page; a suggestion is your product completing the user’s sentence — which is why autocomplete has policy and legal exposure search results don’t (defamation claims, court-ordered removals, and policy classes like hateful/violent/explicit predictions that Google documents publicly). Mechanically it’s two layers with very different latencies:

  • Build-time filter (bulk, slow): during the batch build, drop candidates that match blocklists and policy classifiers (hate/adult/violence/PII patterns), per jurisdiction where required. Cheap here because it’s offline and touches the whole corpus once per build.
  • Serve-time deny-list (tiny, fast): a takedown cannot wait for tomorrow’s rebuild. Keep a small, replicated exact-match set (thousands of entries — it fits anywhere) consulted on every response, pushed via config/pub-sub so a removal propagates in minutes. It also has to be enforced at or after the edge cache, or short-TTL cached entries keep serving the removed suggestion; in practice: filter at the suggest service and purge/expire the affected edge keys.

Privacy: minimum support is a hard floor

Anything a user types becomes candidate input — names, addresses, medical queries. The invariant: never suggest a string seen from fewer than N distinct users (N in the tens-to-hundreds, plus time-window constraints). This one threshold does triple duty: it keeps one person’s query from being echoed to others, it blocks single-source bot campaigns from planting suggestions, and it shrinks the candidate corpus for free. The Zipf tail you refuse to suggest was mostly unsuggestable noise anyway — which is also why §2’s indexed corpus is ~1e9 and not “every distinct string ever typed.”

Fail open: suggest must never take search down with it

Autocomplete is an enhancement to a text box that works fine without it. Encode that asymmetry everywhere: the client sets a hard ~100–200 ms timeout and silently renders nothing on miss (an empty dropdown, never a spinner or an error); the edge serves stale cached lists (stale-while-revalidate) when the origin is slow; the suggest service circuit-breaks per shard — a dead shard means degraded suggestions for its slice of prefixes, not queued requests backing up into the gateway. The SLO conversation writes itself: search availability must be fully decoupled from suggest availability; suggest gets its own (looser) SLO and its own error budget. Saying “this component is allowed to fail, and here is the mechanism that makes its failure invisible” is a staff-level signal.

11 · Interview follow-ups (pre-empted)

  • “Why not LIKE 'pre%' on an indexed column?” A B-tree gives you the prefix range, but you still scan + sort by score per query, at ~350k+ QPS, under a few-ms budget. The DB falls over on both QPS and re-ranking cost. Precomputed top-k in RAM is what hits the latency target.
  • “How do you update one node’s top-k when a count changes?” You don’t, per event. Counts flow through the speed layer; the materialized top-k is refreshed by batch rebuild plus the merged fresh layer. In-place trie edits at write-rate are exactly what you avoid.
  • “Why an FST over a plain trie?” Suffix sharing + bit-packing makes ~2 TB fit in RAM across a small fleet; a pointer trie is several times larger. The cost — it’s build-then-serve, not easily mutated — is fine, because freshness lives in the speed layer, not in mutating the base.
  • “Consistent hashing — what about a single viral prefix?” Hashing balances distinct prefixes, not a single hot one. That’s handled by replicating the hot shard + edge-caching the head (§6, rung 3).
  • “Cache hit rate and TTL?” The head is ~50–70% of traffic in ~10k entries → very high hit rate on a tiny cache; a TTL of seconds–minutes keeps trending fresh while still absorbing the hot keys.
  • “Personalized suggestions?” Candidate generation stays global (prefix → top-k); personalization is a re-rank of that small candidate set with per-user signals — it doesn’t touch the index size.
  • “Multi-language / Unicode?” Index per language/locale (separate FSTs) and route by the lang param; normalize (case-fold, strip accents) before the walk so “cafe” and “café” share a path.
  • “How do you merge batch and fresh scores — they’re on different scales?” Normalize both to rates, apply a capped trend boost (§7): base_rate × clamp(fresh_rate/base_rate, 1, B). The cap and a min-support threshold stop bursts and sketch over-counts from hijacking the box.
  • “A court orders a suggestion removed. What happens in the next five minutes?” Serve-time deny-list pushed via config/pub-sub, enforced at the suggest service, plus purge of the affected edge-cache keys (§10). The build-time filter catches it permanently at the next rebuild. Nothing waits on a 2 TB rebuild.
  • “How does a new index version roll out?” Immutable per-shard segments, load-alongside, warm, atomic pointer flip, canary at ~1% with CTR/empty-rate guardrails, rollback = flip back (§8). Budget the 2× RAM headroom or do a rolling swap through the replicas.
  • “What if the suggest service is down?” Nothing, visibly: client timeout → empty dropdown; edge serves stale; search itself is untouched (§10). Suggest is fail-open by construction.

12 · Real-world examples

Google / YouTube suggest · Elasticsearch/Lucene

Google’s suggest endpoint returns ranked completions on every keystroke at planet scale, blending all-time popularity with trending and personalized signals — the batch-base-plus-fresh-delta shape above. Google’s own writeups on autocomplete confirm the production concerns in §10 are load-bearing: predictions come from real aggregate searches (freshness and locality included), and dedicated policy systems remove violent, hateful, explicit, or unreliable-rumor predictions — i.e. scrubbing is a first-class subsystem, not an afterthought. Lucene/Elasticsearch ship the serving machinery concretely: the FST-backed completion suggester stores weighted terms compactly in memory and returns top-k by weight in a prefix walk, with a context suggester for per-category/locale filtering — a production instance of “materialize top-k, serve from RAM.” The lesson mirrors S14: the interesting engineering is the read/cache and freshness sides; the prefix structure itself is nearly a library call.

LinkedIn Cleo

LinkedIn open-sourced Cleo (2011, Apache 2.0), the library then powering its typeahead for members, companies, groups, and skills — and it’s the instructive counter-example, because LinkedIn’s matching requirement breaks the trie. Name search must be partial and out-of-order: “soft eng” should match “software engineer,” and “jeff w” should match “Jeff Weiner” — there is no single prefix to walk. Cleo’s per-partition machinery: an inverted index from term-prefixes to document IDs generates candidates; a tiny per-document Bloom filter (~8 bytes) cheaply rejects documents that can’t match all query terms; a forward index then eliminates the Bloom filter’s false positives before ranking. The staff-level takeaway: when the matching predicate changes, the structure changes (trie/FST → inverted index + filters), but every invariant of this chapter survives — RAM-resident, partitioned, precomputed candidate generation, and a small candidate set re-ranked at the end.

13 · Key talking points

  • It’s a read/caching problem: precompute top-k per prefix, serve from RAM; aggregate QPS is small (~21 boxes) — memory footprint and skew are the real constraints.
  • Trie to teach, FST to ship; serve-time is really a KV get (prefix → top-k) — the FST is the intra-shard storage format. The load-bearing ideas are materialized top-k and the depth cap (~5–7 chars) that makes the index fit, not the structure name.
  • Derive the size: 1e9 queries × ~20 prefix memberships × ~200 B/entry ≈ 2 TB naive; depth cap + FST bring it to a few hundred GB.
  • First-letter sharding is the trap — raise it, reject it for catastrophic skew → hash(prefix) for structural balance → replicate + edge-cache the head for popularity skew (P2/P11) → two-tier trie.
  • The head is tiny and huge: ~10k prefixes ≈ 50–70% of traffic, so a small edge cache solves most of the hot-key problem.
  • Freshness = lambda/kappa: daily batch base + streaming speed layer (Count-Min Sketch + heavy-hitters + time decay); merge by normalizing to rates + a capped trend boost — never interleave raw counts.
  • Deploys are index swaps: immutable versioned segments, load-alongside, atomic flip, canary with CTR/empty-rate guardrails; budget the 2× RAM headroom. The mixed-version window is fine because ranking was already eventually consistent.
  • Production trio: build-time policy filter + minutes-fast serve-time deny-list (takedowns can’t wait for a rebuild); min-support ≥N distinct users (privacy + anti-manipulation); fail open — client timeout, stale-while-revalidate at the edge, per-shard circuit breakers.
  • Ranking is candidate-gen then re-rank the small set — never score the whole corpus.
  • Boundary: this is suggestion, not retrieval — the actual search is S7.
